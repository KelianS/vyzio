# Instructions de Développement

## Contexte du Projet
Une solution de video-surveillance pour la maison ou les professionnels; **autonome, résiliente et privacy-first**. 
L'objectif est de fournir une reconnaissance faciale IA locale sans dépendre de services cloud tiers pour le traitement des images.
Le projet se différencie par sa souveraineté (Française) et sa vocation plug and play. A destination d'un public non technophiles.

### Engagements
- **Privacy by design** — IA locale, zéro transmission d'images sans consentement
- **Transparence** — Code source ouvert, audit possible
- **Résilience** — Fonctionne sans internet
- **Interopérabilité** — Pas de vendor lock-in
- **Simplicité** — Aucune connaissance technique requise pour l'installation et l'utilisation

## Conventions & Principes
- **Clean code** — Lisibilité, simplicité, modularité
- **Language(s)** — .NET 10 / C# pour le backend. TypeScript + React + Vite pour le frontend. Python si pas le choix / pour IA.
- **Package manager frontend** — pnpm obligatoire (pas npm, pas yarn)
- **Privacy first** — Jamais envoyer d'images sans consentement explicite
- **Modulaire** — Chaque composant (caméra, stockage, IA) doit être pluggable, micro-services ou module indépendant
- **Tests** — Coverage obligatoire : tests unitaires (use cases mockés via NSubstitute) + tests d'intégration (SQLite in-memory)

## Workflow obligatoire

Ce document est la **source de verite** pour le workflow de travail du repo.

Tout changement significatif suit cet ordre. Il est interdit de commencer l'implémentation tant que les étapes documentaires amont ne sont pas alignées.

1. **SPECS d'abord, si le besoin produit change** : user stories, parcours, périmètre MVP.
2. **SAD ensuite, si la solution technique ou les frontières changent** : composants, responsabilités, options retenues.
3. **BACKLOG ensuite** : ordre d'exécution, découpage, dépendances, critères de validation.
4. **Implémentation ensuite seulement** : code minimal, cohérent avec les documents validés.
5. **Tests ensuite** : validation ciblée obligatoire du slice modifié.
6. **Documentation utilisateur ensuite** : toute feature livrable doit être documentée pour l'usage réel.

### Règle pratique
- Si une feature ne modifie ni besoin, ni architecture, ni plan: on peut aller directement à l'implémentation puis aux tests.
- Si une feature contredit un document existant, on met d'abord le document à jour au bon niveau avant d'écrire le code.
- Le backlog n'est jamais utilisé pour découvrir la stratégie après coup; il traduit une stratégie déjà décidée dans les SPECS et/ou le SAD.
- Aucune PR n'est considérée propre si le code est à jour mais que la documentation de cadrage est en retard.

## Role des documents et scope

Chaque document a un role strict. Le but est d'eviter les redites, les contradictions et les documents qui se marchent dessus.

### README.md
- **Role** : porter la vision du projet, le positionnement, la promesse produit et l'etat global du depot.
- **Doit contenir** : le pourquoi du projet, le public cible, les grands benefices, le statut du projet, les liens vers la documentation de reference.
- **Ne doit pas contenir** : architecture detaillee, decisions techniques fines, backlog d'execution, spec fonctionnelle exhaustive.

### docs/SPECS.md
- **Role** : definir le besoin produit et le comportement attendu du systeme du point de vue utilisateur.
- **Doit contenir** : user stories, parcours, regles fonctionnelles, contraintes produit, comportements attendus, perimetre MVP.
- **Ne doit pas contenir** : choix techniques detailles, technologies retenues, decomposition en services techniques, plan d'implementation.

### docs/SAD.md
- **Role** : decrire la solution technique retenue pour satisfaire les SPECS.
- **Doit contenir** : architecture cible, frontieres de responsabilite, ADR, composants, contrats, choix retenus et alternatives ecartees.
- **Ne doit pas contenir** : vision marketing, detail complet des user stories, backlog de sprint, taches d'execution fines.

### docs/BACKLOG.md
- **Role** : transformer les choix deja valides dans les SPECS et le SAD en ordre d'execution.
- **Doit contenir** : phases, stories, dependances, priorites, gates de validation, ordre d'attaque.
- **Ne doit pas contenir** : nouvelle strategie, nouvelles decisions d'architecture non validees, detail technique de bas niveau deja porte par le SAD.

### Documentation utilisateur
- **Role** : expliquer l'usage reel d'une fonctionnalite ou d'un parcours une fois livre.
- **Doit contenir** : mode d'emploi, prerequis, limites connues, etapes de configuration ou d'utilisation.
- **Ne doit pas contenir** : raisonnement d'architecture, dette technique interne, arbitrages de backlog.

### Regle de precedence
- La **vision** vit dans `README.md`.
- Le **besoin** vit dans `docs/SPECS.md`.
- La **solution technique** vit dans `docs/SAD.md`.
- Le **plan d'execution** vit dans `docs/BACKLOG.md`.
- Le **mode d'emploi** vit dans la documentation utilisateur.

### Regle anti-duplication
- Si une information existe deja dans le bon document, les autres documents doivent la **referencer** ou la **resumer tres brievement**, pas la repliquer en detail.
- Si deux documents portent la meme information avec des niveaux de detail differents, un seul doit rester source de verite.
- En cas de doute, on remonte d'abord au bon niveau : vision, besoin, architecture, execution, usage.

## Architecture — Clean Architecture (obligatoire)

Toute nouvelle feature backend doit respecter cette structure de couches. Ne jamais déroger à la direction des dépendances.

```
Core         ← entités domaine + interfaces (ports). Aucune dépendance externe.
Application  ← use cases uniquement. Dépend de Core. Jamais de DbContext ni d'EF.
Infrastructure ← implémentations des interfaces Core (repositories EF, MQTT, HTTP...). Dépend de Core.
Api          ← wiring DI + endpoints Minimal API groupés. Dépend de Application + Infrastructure.
Tests        ← unitaires (NSubstitute, zéro DB) + intégration (SQLite in-memory, EnsureCreated).
```

### Règles strictes
- **Core** : pas d'EF Core, pas d'ASP.NET, pas de packages infra. Entités POCO + interfaces uniquement.
- **Application** : un use case = une classe avec une méthode `ExecuteAsync`. Pas de CQRS ni MediatR. Pas d'accès direct à EF.
- **Infrastructure** : implémente les interfaces de Core. Seule couche autorisée à connaître EF, SQLite, MQTT, etc.
- **Api** : les endpoints sont groupés dans `Endpoints/`. `Program.cs` ne contient que le wiring. Le `DbContext` n'est jamais injecté directement dans un endpoint.
- Les **use cases sont testables sans DB** (mocks NSubstitute sur les interfaces).

### Exemple de flux pour une feature "Profiles"
```
IProfileRepository          (Core/Interfaces)
ProfileRepository           (Infrastructure/Persistence/Repositories) → implémente IProfileRepository
CreateProfileUseCase        (Application/UseCases/Profiles) → reçoit IProfileRepository par DI
ProfilesEndpoints           (Api/Endpoints) → reçoit CreateProfileUseCase par DI
CreateProfileUseCaseTests   (Tests/UseCases) → mock IProfileRepository avec NSubstitute
```
